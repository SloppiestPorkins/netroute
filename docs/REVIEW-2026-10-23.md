# NetRoute review, 23 October 2026

Read-only review of the tree at `main` (working copy, including other agents' uncommitted edits to
`Wfp\**`, `NetRouteEngine.cs`, `Traffic\**`). Line numbers are from the working copy as read; the files
named in the brief as being in flux may have moved by a few lines. Where I am guessing rather than certain
it says **(guess)**. Where I looked at the owner's installed machine it says **(observed)**.

## State of the project

The core idea is sound and most of the careful parts are careful. The WFP struct mirrors are right (I checked
`FWPM_FILTER0`, `FWPM_SESSION0`, `FWPM_ACTION0`, the sublayer and condition layouts against the native
headers by hand and the layout tests pin them), the unmanaged memory in `ConditionScope` lives exactly as long
as it has to, the `IpHelper` / `ConnectionTable` / forward-table offsets are right, the driver wire format is
byte-tested, the dynamic WFP session means a crashed service cannot leave filters behind, the driver is never
stopped, and setup's PATH editing, zip-slip check, installer signature check and driver-never-unloaded rule are
all handled with real thought. The new differential `WfpEnforcer` fixes the one WFP bookkeeping problem I would
otherwise have reported (state diverging from the engine after an aborted transaction).

What worries me is the layer around the kernel: the parts that change Windows state *outside* WFP and have to be
undone.

* The default-route change is not reliably undoable. On the owner's PC today `route-state.json` records
  NetRoute's own metrics as the "originals" (finding 1), so uninstall / emergency-disable would put Windows back
  to NetRoute's settings, not Windows'.
* Emergency Disable is queued behind the same lock as everything else, and that lock is held across multi-second
  PowerShell calls (finding 2).
* The service's shutdown path has a latent error (finding 3) that shows up in the Event Log on three separate
  days, each time coinciding with an update.
* Several things the user is told are stronger than what was established: the self-test, "Verified", the green
  "Protected" header, "Default - Windows decides" (findings 9 to 12).

None of this makes the project a mess. Most of the findings below are small, local fixes. Findings 1 to 3 are the
ones I would do first.

## A. Broken or unsafe (do these first)

### 1. The saved "original" interface metrics are NetRoute's own, so Restore cannot put Windows back (observed)

* `src\NetRoute.Windows\Split\DefaultRouteManager.cs:46-56` (capture), `:76-126` (Restore), `:223-239` (Load/Save)
* **Evidence.** `C:\ProgramData\NetRoute\route-state.json` right now:
  `Originals: [{Wi-Fi 2: Automatic=false, Metric=1}, {Ethernet: Automatic=false, Metric=21}]`. Metric 1 is exactly
  `preferredMetric`, and 21 is exactly what `EnsurePreferred` computes for the other adapter when both route
  metrics are 1 (`1 + 1 + 20 - 1`). Those are values NetRoute wrote, not Windows' automatic metrics. Live
  `Get-NetIPInterface` shows both adapters `AutomaticMetric: Disabled, InterfaceMetric: 1`.
* **What happens.** `Restore()` sets each adapter back to "manual, metric 1" and "manual, metric 21", then deletes
  the file and reports success. Uninstall, Emergency Disable and `cleanup-driver` all say "Windows' default
  connection is back to how it was". It is not: Wi-Fi stays the default route, permanently, with manual metrics
  Windows will never re-tune. The brief's requirement (uninstall leaves networking exactly as it was) is not met
  on this machine.
* **How it got there.** I cannot see the history. Mechanisms in the code that can produce it: `Read(adapter)`
  runs whenever `Load()` returns null, and `Load()` returns null both when the file is absent *and* when the JSON
  is unreadable (`:229`, silently); `Save` is a non-atomic `File.WriteAllText` (`:238`), so a kill during the
  write (setup stops the service while it is mid-reconcile; the 23 Oct 18:45 update is the timestamp on the file)
  leaves a truncated file. After that the next `EnsurePreferred` reads the live (already NetRoute-modified)
  metrics and records those as the originals. **(guess)** which of these it was.
* **Fix.** (a) Write the state file atomically (temp file + `File.Move(..., overwrite)`), as `ConfigStore` already
  does. (b) A corrupt state file must not be treated as "nothing is managed": if the file exists but cannot be
  parsed, restore every connected adapter to `AutomaticMetric Enabled` rather than re-reading. (c) Never record an
  original that is manual *and* equals what NetRoute would have set; treat it as unknown and restore to Automatic.
  Almost every PC had Automatic. (d) Repair this machine: `Set-NetIPInterface -InterfaceAlias 'Wi-Fi 2','Ethernet'
  -AddressFamily IPv4 -AutomaticMetric Enabled`, then delete the file, after the code is fixed.
* **Test.** There are none for `DefaultRouteManager` at all. The class takes `statePath` and an `IAdapterSource`
  so it is testable if `Run` becomes an injectable `IPowerShell`/`INetIpInterface`.

### 2. Emergency Disable waits on the engine lock, which is held across PowerShell calls with 60 s timeouts

* `src\NetRoute.Service\NetRouteEngine.cs` `EmergencyDisableAsync` (~`:259`), `ReconcileLocked` (~`:506-556`,
  `ApplyRedirect` call ~`:544`); `src\NetRoute.Windows\Split\DefaultRouteManager.cs:196-221` (`Run`);
  `src\NetRoute.Ipc\NamedPipeNetRouteClient.cs:51-52` (no response timeout)
* **What happens.** Every engine entry point, including `EmergencyDisableAsync`, takes `_gate`. `ReconcileLocked`
  calls `_backend.ApplyRedirect` under the gate, and a changed plan makes `SplitTunnelController.Apply` call
  `DefaultRouteManager.EnsurePreferred`, which spawns `powershell.exe` five times in series (two
  `Get-NetRoute`, two `Set-NetIPInterface`, one `Find-NetRoute`), each with a 60 s kill timer and the NetTCPIP
  CIM cmdlets, which are the slow, occasionally-hanging kind. So `netroute emergency-disable`, the tray item and
  the GUI button can wait seconds (typically) to minutes (a hung CIM call) with no feedback; the pipe client has
  no read timeout, so the CLI just sits there. The CLI's "service unreachable" fallback only triggers on a
  *connect* failure, which does not happen here because the pipe is up.
* **Second half of the same problem.** `EmergencyDisableAsync` calls `_backend.EmergencyDisable()` first and
  persists `EnforcementPaused = true` only if that returned. If it throws (it does `_split.DisableAll()` ->
  `Restore()` -> PowerShell, which throws on any failure), nothing is paused and the next 10 s tick re-applies the
  whole plan. The undo button un-undoes itself exactly when something is wrong.
* **Fix.** Make the filter removal and driver reset not depend on the gate (own small lock, or call the backend
  before waiting for the gate); persist the pause *before* trying the slow route restore; give the pipe client a
  response timeout so a wedged service becomes "unreachable" and the existing stop-the-service fallback runs. Longer
  term, replace the PowerShell metric calls with `GetIpInterfaceEntry`/`SetIpInterfaceEntry` (the class comment
  rejects this for struct-layout risk; `IpHelper` already does the harder `GetIpForwardTable2`), which takes the
  seconds out of the lock.

### 3. A vanished pipe client can fault the pipe server, and shutdown then rethrows it; every stop also logs a spurious Error (observed)

* `src\NetRoute.Service\NamedPipeServer.cs:42` and `:80-85`; `src\NetRoute.Service\ServiceWorker.cs:26,39-42`
* **Evidence.** Application log, source `NetRoute.Service`: `BackgroundService failed ... System.IO.IOException:
  Pipe is broken ... IpcConnection.WriteAsync`, then "BackgroundServiceExceptionBehavior is configured to
  StopHost", at 14 Sep 20:21:03, 29 Sep 16:45:44 and 29 Sep 17:50:35. Each coincides to the minute with a setup run
  (`C:\ProgramData\NetRoute\logs\setup-*.log`), which kills the GUI first (`CloseApp`) and then stops the service.
  Also, on every one of those stops plus 25 Sep, 27 Sep and 23 Oct 18:45:08: `Policy reconciliation failed
  TaskCanceledException ... NetRouteEngine.ReconcileAsync`.
* **Cause.** The `catch (Exception ex) { await connection.WriteAsync(Failure(ex), ct); }` handlers in `ServeAsync`
  write to a pipe whose client has already gone; that throws `IOException` out of `ServeAsync`, nothing observes the
  task, and it stays in `clients` until the next accept does `clients.RemoveAll(t => t.IsCompleted)`. If it is
  still there at shutdown, `await Task.WhenAll(clients)` (`:42`) rethrows it, `ExecuteAsync` faults, and the host
  stops with an error. Separately, `ReconcileSafely` catches `Exception` and so logs the normal cancellation at
  shutdown as `LogError`.
* **What happens.** A routine update/stop can end the service as a failure rather than a stop; the Event Log
  fills with errors on every stop, which buries real ones. **(guess)**: setup's `failure reset= 0 actions= ""`
  workaround in `StopService` (`SetupEngine.cs:581`, "NetRoute is configured to restart itself five seconds after
  it ever stops") was written because of this: a service that exits non-zero can be restarted by SCM. If so,
  `netroute emergency-disable`'s fallback (`Program.cs StopServiceFallback`, which does `service.Stop()`) could be
  undone five seconds later by SCM restarting the service with the full plan. The SCM failure events I could see
  (Event ID 7031) are all from the 26 Sep crash loop and none since, so I have not seen this happen, only that the
  precondition is real.
* **Fix.** Wrap the writes in the `catch` blocks of `ServeAsync` in their own try/catch (a client that left is not an
  error); make `RunAsync` `await Task.WhenAll(clients)` inside a try that swallows non-cancellation faults; have
  `ReconcileSafely` ignore `OperationCanceledException` when `ct.IsCancellationRequested`. Consider
  `HostOptions.BackgroundServiceExceptionBehavior = Ignore` for the non-critical hosted services (history, link
  quality, updater): today a bug in any of them stops the enforcement service (`StopHost` is the default and is
  what the log shows).

### 4. Setup relaunches itself and then reports success before anything has happened

* `src\NetRoute.Setup\App.xaml.cs:68`, `:76`, `:110-125`
* **What happens.** When setup needs elevation, or when the uninstaller copies itself to `%TEMP%` (always the case
  for `Uninstall NetRoute.exe`), `Relaunch` starts the child and returns 0 without `WaitForExit`, and `OnStartup`
  does `Shutdown(Relaunch(...))`. So `"Uninstall NetRoute.exe" /uninstall /quiet` (the `QuietUninstallString` setup
  registers for Settings > Apps and winget) exits 0 immediately while the real work runs detached. The README's
  promise ("`/quiet` ... exits 3010 if a restart is needed", exit 1 on failure) cannot hold for uninstall, and not
  for a non-elevated `/quiet` install either.
* **Fix.** For the relocated copy and the elevated relaunch, wait for the child and return its exit code
  (`process.WaitForExit(); return process.ExitCode`), at least when `/quiet` is present.

### 5. Setup's rollback does not undo all of what an update does

* `src\NetRoute.Setup\SetupEngine.cs:157-185` (RollBack), `:55-153` (Install), `:270-285` (RegisterService), `:575-585`
* **a. Recovery actions are not restored after a failed update.** `StopService` strips the service's failure
  actions first (`:581`); only `RegisterService`, which is step 4, puts them back. If step 2 (copy files) or step 3
  throws, `RollBack` restarts the old service but never calls `sc failure ... restart/5000/...`. The PC is left
  running the old version with no auto-restart.
* **b. A failed *fresh* install is not rolled back.** `RollBack` only acts when `Directory.Exists(backup)`
  (`:162`); on a clean PC there is no backup, so a failure in the driver step or the service start leaves the new
  files, the driver service (`start= auto`), disabled Mullvad daemons and possibly a registered service in place,
  with no uninstall entry (that is written in the last step) for the user to remove them with.
* **c. Steps 5 and 6 (shortcuts/PATH, uninstall registration) sit outside the try/rollback block.** A COM failure
  creating the shortcut leaves the new version live, `.old` and `.new` folders behind and no Settings > Apps entry.
* **d. (guess)** After uninstalling NetRoute and reinstalling before the restart that removes the old driver
  service, `sc config mullvad-split-tunnel ...` fails with "marked for deletion" (1072); `SetUpDriver` turns that
  into a generic "couldn't be set up" warning that does not say "restart first".
* **Fix.** Restore the failure actions in `RollBack`; make fresh-install failure remove what this run created
  (service, files, driver service if `DriverCreated`), or at least write the uninstall registration *before* the
  risky steps so the user can remove a half-install; move steps 5 and 6 inside the guarded block or make them
  non-fatal warnings (they are not worth rolling the product back for); detect "marked for deletion" and say so.

### 6. Uninstall removes the thing that could restore Windows even when it could not

* `src\NetRoute.Setup\SetupEngine.cs:328-331`, `:353-370`
* **What happens.** If `netroute cleanup-driver --remove-sublayers` fails, step 1 only warns ("Some network
  settings couldn't be put back"). Step 4 then deletes the install folder (including `netroute.exe`), the
  `SOFTWARE\NetRoute\Setup` state key, the service and the driver registration. If the route restore was the
  failure (finding 1), nothing is left that knows how to undo it, and the user is not given the one-line manual
  command. If `netroute.exe` is missing (partial install) step 1 is skipped as "Nothing to restore" even if
  `route-state.json` exists.
* **Fix.** Do the metric restore from setup itself (it only needs `route-state.json` and `Set-NetIPInterface`), or
  keep going but print the exact PowerShell line that puts back Automatic metrics when the restore fails; do not
  mark the step as skipped just because the CLI is gone.

### 7. If WFP is not ready when the service starts, enforcement stays off until someone restarts it

* `src\NetRoute.Service\ServiceRegistration.cs:22-35`; service is created without a dependency
  (`SetupEngine.cs:270-285`; no `depend=` anywhere in `scripts` or `src`)
* **What happens.** The backend is chosen once, in a singleton factory. If `WfpSession.CanOpen` or the constructor
  fails, the service runs the rest of its life as `NullEnforcementBackend` ("NetRoute needs administrator rights"
  is the default text, which is wrong for a boot race). Nothing retries. The service is `start= auto` with no
  dependency on `BFE` (the Base Filtering Engine), the standard thing for anything that opens `FwpmEngineOpen0` at
  boot. **(guess)** that BFE can lose that race on a given boot; I have not seen it fail, but nothing prevents it.
* **Fix.** Add `depend= BFE` in `RegisterService`; make the backend lazy/retrying (open on first reconcile, retry
  with the existing backoff) rather than permanent; and say which error actually occurred.

### 8. The first reconcile runs on the host's start-up path **(guess)**

* `src\NetRoute.Service\ServiceWorker.cs:15`
* `ExecuteAsync` calls `await ReconcileSafely(...)` before its first real suspension (the semaphore wait completes
  synchronously), so the whole first apply, including `EnsurePreferred`'s five PowerShell launches and the driver
  start (up to 5 s), runs inside `BackgroundService.StartAsync`, i.e. before the service reports Running. SCM allows
  about 30 s; a slow boot or a hung CIM call is error 1053 and a crash loop. The commit history ("Fix the service
  never staying up", the 26 Sep loop) shows this service has had start-up trouble. `await Task.Yield();` at the top of
  `ExecuteAsync` is a one-line fix and also lets the pipe come up first.

### 9. IPC reads the response one byte at a time, caps a line at 1 MiB, and the connection list is unbounded

* `src\NetRoute.Ipc\IpcConnection.cs:15,9`; `ConnectionVerifier.GetConnections` (`src\NetRoute.Service\ConnectionVerifier.cs:22`)
* `ReadAsync` does `await _stream.ReadAsync(one, ct)` per byte into a `List<byte>`. A status response is tens of
  KB and the GUI asks every 2 s; the live-connections response is hundreds of KB. That is hundreds of thousands of
  async pipe reads per poll, in the GUI process (and some in the service) on a machine where you are chasing
  frame-time spikes. Use a `StreamReader` / `PipeReader` (or a pooled buffer and `IndexOf('\n')`).
* The cap is 1 MiB and `GetConnections` returns every non-loopback TCP and UDP row. At roughly 300 bytes a row that
  is about 3,500 rows: a torrent client or a busy browser plus Steam gets there. **(guess)** on the exact row count,
  but the client has no handler for `IpcLineTooLongException` (it is not an `IOException`), so the Live view would
  fail with a raw exception. Page or cap the list server-side.

## B. The user is told more than has been established

### 10. The self-test proves the PC has two internet lines, not that NetRoute does anything

* `src\NetRoute.Service\SelfTest.cs:211` (message), `:234-248` (egress probe), `:176-216` (load test);
  `NetRouteEngine.cs` `StartSelfTestAsync` (~`:417`, "Apps are being moved")
* Steps 1, 2 and 4 bind sockets *from the service itself* to each adapter's IPv4 address
  (`BoundClient(local, ...)`). The service is not a rule, and an explicitly bound socket goes out of its adapter
  with NetRoute uninstalled. So the "different public addresses" and "a download on one connection can't take the
  other one's latency" results are properties of the two ISPs. Step 4's pass text ("That's the separation
  working") credits NetRoute with it. It would pass identically if the service were stopped.
* Step 3 passes if *any* app is Verified, and `Verified` includes Downloads-role apps, which are not moved at all.
* **Fix.** Either rename the test to what it measures ("Do your two connections interfere with each other?") and drop
  "that's the separation working", or make it exercise NetRoute: launch a probe process from a path that has a
  temporary Gaming rule and check where *its* unbound socket's traffic egresses (the POC `split` command already
  does this and is the real proof). The README line "`netroute selftest` prove the separation, end to end" should
  match whichever it becomes. Restrict step 3 to Gaming-role apps.

### 11. "Verified" means "a socket exists", and several statuses are the plan restated

* `src\NetRoute.Windows\Traffic\TrafficVerdicts.cs:107-114`, `:77-91`, `:74`; `TrafficObserver.cs:57-95`;
  `src\NetRoute.App\ViewModels.cs:164-202`
* **Verified.** It is set when any matching socket's *local address* belongs to the expected adapter. The tables
  include bound-but-idle UDP sockets (an app's mDNS/SSDP socket bound to the adapter address counts), and one
  attributed socket is enough even when the app's other sockets are wildcard-bound and unattributed. The brief says
  never to call a rule protected because a filter exists; this calls it verified because a socket exists. It is
  better than the filter check, but the word is "traffic" (brief section 24) and what was observed is "sockets".
  Cheap improvement: count only TCP `Established` rows or UDP rows with an active ETW rate (the meter already has
  per-process, per-adapter bytes), and word the summary "seen using".
* **Blocked.** `State = Blocked` and "Traffic blocked by Kill Switch" are produced from the plan alone, with no
  observation that anything was refused. `LeakObservation.Blocked` is always `false` (`:74`) and nothing sets it,
  so the brief section 25 "Action: BLOCKED" case does not exist. Either delete the field or implement it (WFP net
  events).
* **Header.** The green "Protected" (`ViewModels.cs:201`) is shown with zero rules, with every app "Applied" and
  no traffic yet, with `RedirectionAvailable == false` (only a banner is added) and with the redirect "Off". With the
  driver down and Downloads as the default route (finding 12), a Gaming app is pinned to a line it cannot reach, so
  it has no network at all; the header still says Protected. It should be amber when Gaming rules exist and the
  driver is not engaged.
* **System downloads** ("Windows and Xbox downloads use Downloads", `Checkup.cs:167`) are derived from the plan too;
  no observation backs "kept on Downloads".

### 12. Default means "Windows decides", but NetRoute silently makes the Downloads line the default for everything unlisted

* `src\NetRoute.Core\Policy\RedirectPlan.cs:68` (`ManageDefaultRoute = true` for any two distinct connected
  adapters, no rules needed); `src\NetRoute.App\ViewModels.cs:818` ("Default / Windows decides");
  `README.md:28` ("Downloads is whatever Windows already treats as the default route");
  `PolicyResolver.cs:94-98` ("NetRoute is deliberately not interfering")
* **What happens.** As soon as setup completes, NetRoute rewrites IPv4 interface metrics so Downloads wins. The metric
  change is persistent (survives reboot, survives a service crash). Anything not in a rule, a game you have not
  added, Discord voice, Spotify, a new browser, all DNS (docs/SPLIT-TUNNEL.md admits "DNS lookups ... follow the
  default route") goes out of the Downloads line, including while a download is saturating it. That is the
  opposite of the product's promise for exactly the traffic nobody added. The README says the reverse of what the
  code does, the UI says "Windows decides", and the resolver says "not interfering".
* This is a design decision, not a bug, and it may be the right one given the driver's one-tunnel-address limit. It
  has to be said out loud: in the README's "Honest limits", at first-run, and in the "Default" tile ("Downloads line
  unless you add it"). Also consider making `ManageDefaultRoute` conditional on there being at least one Gaming rule
  that needs splitting.

### 13. `KillSwitch` is a flag that changes nothing, and the text contradicts the behaviour

* `src\NetRoute.Core\Policy\PolicyResolver.cs:175-186`; `src\NetRoute.App\ViewModels.cs:1077`; `AppRule.cs:31`
* Both branches return `BlockAll`; the "Kill Switch is off" line says traffic is blocked "while the network is
  down", which is what Kill Switch on does. The UI always sets `KillSwitch = !FallBackWhenDown`, so the flag is
  only ever the inverse of `Mode == Strict`. Delete `KillSwitch` (keep `Mode`), or make it mean something.
* The same applies to `EnforceIpv4`, `EnforceTcp`, `EnforceUdp` and `IncludeRelatedProcesses`: nothing sets them from
  the UI, CLI or IPC, they are in the fingerprint and `FilterPlanner`, and `IncludeRelatedProcesses` does nothing
  at all. Keeping unreachable per-protocol branches in the filter planner is cost with no user. Remove, or cut
  them from the planner and keep only IPv6.

### 14. The connection history's "nothing leaves the machine" is not true, and it runs whether anyone looks or not

* `src\NetRoute.Service\ConnectionHistory.cs:29` (the claim), `:47` (`Dns.GetHostEntryAsync`), `:76`, `:94`
* Every five seconds, forever, every remote address any program has a socket to is reverse-resolved. A PTR query
  to the Windows DNS server (the Downloads line's resolver, finding 12) for each game server and peer IP, plus
  LLMNR/NetBIOS fallbacks for private addresses. That is an ISP-visible list of every address your games talk to,
  contradicting the comment and the brief's "no telemetry". Resolve lazily, only for the addresses the History
  panel is currently showing, and only while the panel is open.

### 15. Messages that send a stranger to files they do not have, and a feed that has shipped a zero hash

* `src\NetRoute.App\ViewModels.cs:216`, `:445`; `Checkup.cs:83`; `MainWindow.xaml:556`: "Run RUN-NETROUTE-SETUP.cmd /
  INSTALL-NETROUTE.cmd". Those scripts live only in the git repo (`scripts\`); the installer does not carry them.
  Replace with "Repair NetRoute" (rerun the installer) or the in-app action.
* **(observed)** Application log 27 Sep 04:14:55: the updater rejected a download because the feed's sha256 was 64
  zeros. The updater did the right thing, but a feed with a placeholder hash was published, and the CI check in
  `.github\workflows\build.yml` (`^[0-9A-Fa-f]{64}$`) accepts it. `dist\updates.json` currently contains the template
  note "Edit this line: it is what the app shows beside the version." which would show verbatim in every user's banner.
  Have `build-installer.ps1` fail on an all-zero hash or the placeholder note, and have CI download the release asset
  named by `updates.json` and compare hashes (or at least check the file exists and the size matches).
* `netroute quiet-hours 25 99` prints "between 25:00 and 99:00" while the engine stores 23 and 23
  (`NetRouteEngine.cs` `SetQuietHoursAsync`, `Program.cs:84`); `from == to` is silently "never". Validate in the CLI and
  print what was stored.

## C. Cost on a gaming PC

### 16. A connection snapshot opens a process handle per *socket*, every 5 seconds, whether anyone is looking

* `src\NetRoute.Windows\Traffic\TrafficObserver.cs:86,90`; `ProcessIdentityCache.cs:39`; callers:
  `ConnectionHistory` (5 s, always), GUI status (2 s visible / 10 s hidden), `GameInPlay` (every reconcile when
  pause-while-gaming is on)
* For each row of the four connection tables it does `OpenProcess` + `GetProcessTimes` + `CloseHandle` (to validate
  the PID's creation time) and builds a string key from two `IPEndPoint.ToString()` calls. Thousands of rows means
  thousands of handle opens and tens of thousands of short strings per snapshot. The 1 s cache does not help the 5 s
  caller. Resolve per distinct PID once per snapshot (rows are not sorted by PID, so use a local dictionary), skip
  the string key (use a struct key of protocol/endpoints/pid), and do not run the history recorder unless a client
  is looking at History (or at least back it off to 30 s).

### 17. Other constant background work

* GUI poll (`MainWindow.xaml.cs:45,50`): the hidden tray window still calls `GetStatus` every 10 s. Each status call
  re-reads and re-parses `config.json` from disk (`ConfigStore.Load` has no cache), calls `DiscoverAll()` (a
  `GetAdaptersAddresses` plus ~40 allocations per adapter), `GetIpForwardTable2`, and snapshots the connection
  tables, all under the engine gate. A tray-only GUI could ask every 30 to 60 s, or the service could push.
* `ReconcileLocked` calls `DiscoverAll()` three times per tick (resolver, `RecordHealthTransitions`,
  `RedirectPlanner.Build`), every 10 s. Pass one snapshot through.
* `Downloading()` (`NetRouteEngine.cs` ~`:455`) refreshes Steam's manifests (every `appmanifest_*.acf` in every library,
  `File.ReadAllText` + regex each) every time a status request arrives more than 10 s after the last. With the GUI
  hidden that is every 10 s forever, touching every library drive; the class comment itself warns that a sleeping
  drive stalls. Only refresh while the Downloads panel is visible.
* `LinkQualityMonitor.cs:56-88`: pings 1.1.1.1 from every connected adapter every 3 s for the life of the service,
  with no GUI open. Small, but it is unconditional traffic to a third party on the line you are gaming on, and it is
  not mentioned in the README next to "never calls anywhere". Pause it when no client has polled recently.
* `ProcessNetworkMeter.cs:136-147` (**guess**, measure first): an ETW `NetworkTCPIP` kernel session that handles
  *every TCP/UDP send and receive event* in managed code (and allocates an `IPAddress` per event via `saddr/daddr`)
  for the life of the service. During a gigabit Steam download that is tens of thousands of callbacks a second on the
  box you are trying to keep quiet. It exists to feed `UsageHistory` and the Live view; consider starting it only
  while a client is polling rates, or sampling `GetPerTcpConnectionEStats` instead (already used by the latency probe).

### 18. Every Gaming/Downloads address change re-runs the five PowerShell calls

* `src\NetRoute.Core\Policy\RedirectPlan.cs:35-41` (`Fingerprint` includes both adapters' IPv4 *and IPv6* address);
  `src\NetRoute.Windows\Split\SplitTunnelController.cs:43,53`
* The driver does need the current addresses, but the *metric* change does not depend on them. Any DHCP address
  change or rotation of the "first non-link-local IPv6 address" (`AdapterDiscovery.Map` takes the first, which may be
  a temporary address) takes a different fingerprint, so `EnsurePreferred` runs again: five `powershell.exe`
  launches under the gate. `NetRouteEngine.Fingerprint` has a long comment about avoiding exactly this for filters.
  Split the route fingerprint (LUIDs only) from the driver-address fingerprint.

## D. Safety of the less-dangerous-but-real parts

### 19. Update path: the pipe lets any interactive user set the feed, and the folder protection fails silently

* `src\NetRoute.Service\NamedPipeServer.cs:57` (all `INTERACTIVE` users get ReadWrite); `Updater.cs:340-362`
* Any signed-in standard user (or anything running as one) can call `setUpdateSettings` with a feed of their choosing.
  The sha256 the updater enforces comes from that same feed, so it proves integrity against corruption, not
  provenance. The remaining barrier is the owner clicking "Install now" and accepting the UAC prompt for an unsigned
  exe. Consider restricting the settings and rule-changing commands to administrators (check the client token on the
  pipe: `RunAsClient` / `GetImpersonationUserName`), leaving read-only commands to everyone. On a one-person PC this
  is theoretical; for "a stranger who installs this" on a family PC it means any account can switch off the
  administrator's policy.
* `Protect()` swallows all exceptions with the comment that inheritance still keeps users out. That is true for a
  folder SYSTEM created. **(guess)** If a standard user pre-creates `C:\ProgramData\NetRoute\updates` (ProgramData
  lets users create subfolders) they own it, SYSTEM's `SetAccessControl` can fail, and they can swap the installer
  after the hash check. The app re-hashes just before `runas` (good), but there is a gap between that hash and
  `Process.Start` (`Updates.cs:44`). Fix: have the service create the folder at install time (setup, which is
  admin), refuse to use it if its owner is not SYSTEM/Administrators, and have setup itself verify the hash of its
  own file before doing anything.

### 20. Unrelated-but-adjacent: the pipe client trusts whoever owns the pipe name **(guess)**

* `src\NetRoute.Ipc\NamedPipeNetRouteClient.cs:75`
* If the service is not running (stop, crash, install window), any user process can create `NetRoute.Service.v1` and
  answer `getUpdateSettings` with a `ReadyPath` and `Sha256` of its own file; the app hashes it, finds a match, and
  runs it elevated. Low likelihood (needs the service to be down at the right moment) and the UAC prompt still
  names an unknown publisher, but a client connecting to a SYSTEM service should check the server's identity
  (`NamedPipeClientStream.GetImpersonationUserName` is SYSTEM, or `PipeSecurity` on connect).

## F. Tests (246 passing)

What is good: pure logic is well covered (policy resolver, redirect planner, protocol serialisation, struct layout,
traffic verdicts, local-network ranges, retry/backoff, differential WFP apply with a fake store, updater parsing).
Few tests sleep on the wall clock (`ConnectionHistoryTests.cs:85,92,133` use `Task.Delay(50)` to "let the failure be

What is not covered and matters:

1. **`NetRoute.Setup` has no tests at all.** Install, rollback, `Existing.Suggested`, `Machine.EditPath`, `StopService`

   would catch. `Payload.Extract`'s zip-slip guard needs one test.
2. **`DefaultRouteManager`**: the save-before-change contract, restore with an absent adapter, corrupt state file,
   LUID change mid-flight, `ResolveTie` interacting with saved originals. Finding 1 would have been caught.
3. **`SplitTunnelController`** (reset-on-disengage, retry-on-failure, handle gone bad). It takes a concrete
   `SplitTunnelDriver`; an `ISplitDriver` seam would make this testable without the kernel.
4. **Updater** download path: the one property the README stakes its security story on, "a download that hashes
   differently is deleted", is not tested. Only `Read` is.
5. **Emergency disable** through the engine (finding 2): no test that it works while the gate is held, or that a
   throwing backend still leaves the app paused.
6. **`NamedPipeServer`** with a client that disconnects mid-response (finding 3), and with an oversized response
   (finding 9).
7. **`TrafficObserver`** end to end: PID reuse, a socket that moves adapter, and (finding 11) an idle UDP socket
   not counting as Verified.
8. `TrafficVerdicts` is tested for Verified/Leak/Configured but not for the pre-existing-connection boundary
   (`FirstSeen == policyAppliedAt`).

Tests that assert the implementation rather than behaviour: I only skimmed `WfpEnforcerDiffTests` (its fake store
is good: it rolls back on a failed commit and asserts adds happen inside a transaction), so I cannot say how much
it pins exact filter lists. Worth a look once the rewrite settles: assert properties that matter (each pinned app
has a permit on its adapter and a block elsewhere, IPv6 handled, loopback and local-network permits outrank
blocks) rather than exact filter names and weights. The layout tests (`WfpStructLayoutTests`) are the good kind:
hard-coded native numbers.

Machine dependence: `TrafficTests.cs:29-42` read the real TCP/UDP tables (fine, they create their own sockets);
`SplitTunnelProtocolTests.cs:119` captures this process via `ProcessSnapshot`; `RedirectPlannerTests.cs:123` uses

the last one that did was fixed). `UpdaterTests` pins the current version to `1.1.0` literally, which is
fine today and will quietly stop meaning anything once releases pass it.

## G. Hand-off notes for the WFP rewrite in progress

I did not report on the old `WfpEnforcer.Apply` (it is being replaced). Things to check in the new one:

* `EmergencyDisable` returns early when `_installed.Count == 0`. If an earlier `Apply` committed but the process
  lost track (exception after commit, before `_installed = working...`), the filters exist and Emergency Disable
  skips them. The dynamic session cleans up at exit, but not before. Better: when asked to disable, enumerate by
  provider key (`FwpmFilterCreateEnumHandle0` with `FWPM_PROVIDER_KEY`) and delete everything of ours.
* A rule whose filters partly fail is rolled back to *none*, which for a Strict Gaming rule means that app is
  unfiltered while the UI shows an error on that app only. Make sure the status says "NOT protected" and not just
  "failed", and consider a block-all fallback for that rule.
* `CollapseProgramFilesByDefault = false` with the OR-semantics POC outstanding: fine, but it means ~1,500 filters for
  this config is the shipping behaviour; the diff-apply is what keeps that survivable.
